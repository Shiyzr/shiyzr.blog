## 目标

我们的目标是：输入一句话（prompt），让模型顺畅地“接着往下写”，直到一段完整的内容结束。

首先，生成什么时候才算结束呢？

- 人工限制：由你设置的 max_length 决定（防止跑太久、浪费算力）。
- 模型决定：由模型预测出的 <|endoftext|> 决定（代表“内容在逻辑上已经结束”）。

模型具体是怎么“一点点顺出后面的内容”的？

- 根据当前 prompt 预测下一个 token。
- 把新 token 接到原 prompt 尾巴上，拼出一个更长的 prompt。
- 再用这个新 prompt 继续预测下一个 token。
- 如此循环，直到出现 <|endoftext|>，或者你设的 max_length 把它强行拽住。

## 什么是 Token？

上面提到了 *token*，这到底是什么？

- 粗暴地讲，token 就是模型眼里的“一个基本单位”，是它读进去、吐出来的东西。
- 表面上看，每个 token 像一个小字符串，比如 "hello"、"world"、"!" 之类。
- 但它既不是“一个字”，也不一定是“一个完整单词”，更不是“一个 byte”那么简单。

举几个例子：

- "hello world" 可能被切成两个 token："hello" 和 "world"。
- "looking" 有可能被拆成 "look" 和 "ing"。

所以，对人类来说是一句很自然的英文，对模型来说是一串 token 编号；你心里想着“语言”，它心里盘算的是“整数序列”。

## 为什么不能直接喂原始文本？

对于模型来说，直接把原始文本塞进去是行不通的，主要有两个原因。

1. 计算机只会算“向量”，不懂什么是“语义”

- 从硬件角度看，计算机就是一个巨大且花里胡哨的计算器，只会对数字搞矩阵运算。
- “苹果”这个词对我们来说是水果，对机器来说只是几个字节，根本没法拿来直接乘一个权重矩阵。
- 所以需要 token 这个中间层：先给每个 token 一个唯一 ID，再通过 Embedding（嵌入层）把这些 ID 变成向量，模型才勉强有东西可以算。

2. “词典大小”和“计算效率”是死对头

如果完全不分词、直接用某种方式把文本丢给模型，大致会走向两个极端，它们都有致命问题：
- 按字/字母输入（Character-level）：
  - 好处是词表很小，几百上千个符号就够了。

  - 缺点：序列会变得极其长。比如单词 "Transformer" 有 11 个字母，如果按字母输入，模型要处理 11 个时间步。Transformer 的计算复杂度和序列长度的平方成正比，序列一长，计算就会慢得吓人，还非常吃显存。

- 按完整单词输入（Word-level）：
    - 乍一看挺优雅：“一个单词一个 token，多清爽”。
    - 缺点：词典会变得极其庞大。英文里有几百万单词（还有各种变体如 look, looking, looked），模型需要维护一个巨大词表，参数量和内存占用都要爆炸。而且一旦遇到词表里没有的新词（Out-of-vocabulary），模型就会直接“看不懂”。

## 文本是怎么被切成 Token 的？

既然我们认命要先把文本切成 token 再喂给模型，那问题就变成了：怎么切才算不亏？

从直觉上看，我们想要的是这种感觉：

- "hello world" -> "hello" "world"
- "looking" -> "look" "ing"

如果直接在“所有可能的切分方案”里找最优解，会非常恐怖：一段长度为 $N$ 的字符串，理论上可能有 $2^{N-1}$ 种切分方式。要在海量文本上暴力搜索哪种切法最好，几乎不可能；而且“什么叫好”本身也很难定义。

于是，大家提出了两条思路：

- 自上而下（切分）：
    > 事实上，存在一种自顶向下的切分方法，叫做 Unigram Language Model Tokenizer。大致思路是：先给一个超级大的词表，然后不断删掉对语言模型损失影响最小的词，最后保留一个“最划算”的子集。

- 自下而上（合并）：
    - 从最细碎的字符开始，通过统计相邻字符/子串的频率来决定谁应该“结成一个更大的单元”。频率越高（“关系越密切”）的两个片段，就越应该合并成一个新的 token。
    - 这是一种贪心（Greedy）的策略，计算上非常高效。

一种非常经典的自下而上的方法叫 BPE（Byte Pair Encoding，字节对编码）：

- 起点是一个只有最小单位的词表（比如所有单个字符）。
- 在大语料里疯狂扫一遍（注意，这里就出现了很多可以优化的点），找出“相邻的两个符号”里出现频率最高的一对，把它俩合成一个新的 token。
- 把这个新 token 加回词表，然后再来一轮统计，再合并频率最高的一对。
- 如此反复，人为控制“合并多少次”，词表也就慢慢长成一个既不会大到离谱、又能比较好表达常见片段的集合。
- 至于 BPE 的公式推导和各种实现细节，放到后面展开会更顺，这里先把直觉建立起来。

## 从数据到模型：最小流水线

如果把前面的内容粗暴压缩一下，我们其实就是在搭一条“从人话到模型”的流水线：

1. 先搞到一堆训练数据（正常人话就行）。
2. 选一套切分方案（比如 BPE，或者别的 tokenizer），根据这套方案，构建一个词汇表，用来把 token（字符串形式）映射到一个个整数 ID。
3. 用词表和 tokenizer 把原始文本啃一遍，变成一长串 ID 序列。
4. 把这些 ID 序列丢给模型（例如一个 Transformer），反复训练，最后得到一个“见过世面”的语言模型。
